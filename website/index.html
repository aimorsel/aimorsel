给 Agent 用

让 Agent 自己去翻，而不是把整本塞进去

内置 MCP Server，一行注册就多出 8 个工具。文档留在本机，Agent 只取需要的部分。

# 注册（Claude Code）
$ claude mcp add aimorsel -- morsel mcp

# 之后 Agent 自己会这么用
get_outline("年报.pdf")
get_section("年报.pdf", "财务摘要")
search_documents("毛利率")

工具它做什么
get_outline只返回标题树、每节页码与 token 估算——读大文档的第一步
get_section按标题取某一节正文，标题模糊匹配
search_documents跨已转换文档检索，命中带页码与标题路径
read_pdf_markdown小文档一次读完，直接返回正文
extract_tables把所有表格以 CSV 文本返回
get_chunksRAG 分块 JSONL，每块带页码与标题路径
qa_check逐页统计，标出空白页、疑似扫描页、低密度页
convert_pdf转换并返回产物清单；没变过的文件直接命中缓存

批量

一千份文档，不用守着

中途断电、临时加文件、隔天再跑——接着上次继续，不重复劳动。

断点续传
只转新的和改过的；换了输出格式或参数会自动重转
多进程并发
几十份以上明显更快，坏文件不拖垮整批
监听文件夹
丢进去就转；文件还在拷贝中会等它稳定
转换报告
每批一份 CSV：状态、页数、耗时、失败原因，Excel 直接打开
失败有下限
引擎解析不了的文件降级成纯文本兜底，而不是留个空目录

自有评测

数字都在仓库里，每一行都能自己复算

731 份公开语料 × 5 个引擎 = 3224 条记录。真值直接从源文件解析（arXiv 的 LaTeX 源码、法规的 HTML 版、合成件的已知结构），不是人打分，也不用大模型当裁判。

引擎 能吃的输入 731 份里转成功 文本相似（双方都成功的文档上，对手 / 我们） 中位耗时
AImorsel全部 8 类格式731（100%）—1.6 秒/份
docling与我们相当299 / 300（分层子集）0.841 / 0.83911.2 秒/份
pymupdf4llm只吃 PDF293（40%）0.775 / 0.7737.2 秒/份
markitdown除图片与扫描件外的多数格式539（74%）0.715 / 0.8420.8 秒/份
pdfplumber只吃 PDF，纯文本289（40%）0.574 / 0.7780.5 秒/份

不支持的格式按失败计——这一列衡量的是「一个混装文件夹丢进去，多少份能出东西」。 与 docling、pymupdf4llm 的文本保真度基本持平，耗时差一个数量级（docling 峰值内存 p95 2.0 GB，我们 620 MB）。 另有一项静默事故只有我们和 docling 没犯：markitdown 与 pdfplumber 把 10 份阿拉伯语文档按视觉序输出， 字一个不少，但检索和分词全部失效。

两处必须说清楚。docling 约 11 秒一份，全量跑不完，只跑了 300 份分层子集，它那一行的份数与别人不同； 在 77 份「所有引擎都成功」的交集上，docling 与 pymupdf4llm 的文本相似度高于我们（0.92 / 0.92 对 0.82）， 那份子集样本小且偏向标准单栏 PDF——结构指标在同一张表上是我们领先。两张表都在结果页里。 最弱的一环是扫描件与图片：数字保真在有文字层的文档上是 0.891，走 OCR 通道只有 0.716， 扫描件里的数字适合检索定位，不能直接进表格。
